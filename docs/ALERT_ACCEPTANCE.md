# 异常提醒流程验收（alpha.5）

自动验收入口：

```sh
./scripts/cargo-local.sh test -p guard-service --test alert_acceptance
```

模拟使用真实 Controller、Monitor、共享 `alerts::deliver_pending` 和可切换阶段的 Platform fixture；OS 通知出口替换成记录器。没有真实进程、网络请求、OS 通知、Claude 或账号。虚拟时钟的时间不是实机响应 SLA。

| 模拟场景 | 验证行为 |
| --- | --- |
| 系统代理关闭、端口消失、进程身份异常、路由失败 | 下一个模拟本地周期首次一条 Problem；重复失败不刷屏；采样继续；本地失败不发出口请求 |
| 同地区 IP 改变、出口地区不符、curl 超时 | 在模拟出口周期发现并保持约30秒请求节流；不展示完整IP；重复故障去重 |
| 新的有效代理 PID、路由或同地区出口稳定 | 先显示恢复观察；两次真实出口采样时间跨度至少30秒且期间本地采样连续后，才一条 Recovered |
| 路径变化、休眠、唤醒 | 即时使旧检查失效；重复信号去重；后台继续采样 |
| 恢复期间再次失败、采样空窗 | 清除候选恢复证据，不能拼接两个零散好样本宣称稳定 |
| 多轮故障恢复 | 每轮一条异常和一条恢复；队列只消费一次，事件保留最近8条 |
| 所有场景 | 不执行启动器，消息/快照不含完整IP、原始路由和进程指纹；恢复始终不解除启动锁 |

额外纯回归覆盖：

- 第一个好出口样本保留异常并显示“恢复观察中”。
- 慢的后置本地检查不能用回调时间扩充真实出口观察跨度。
- 事件使进行中的旧全检失效、阻塞采样期间时效维护仍能取消放行。
- 通知授权乱序、停止后回调、提交超时仲裁、旧测试/旧通知中心查询、系统接收不等于人工收到。
- 处置指引只是展示，不能改变规则严重性、报告时效或手动启动意图。

## 恢复和启动是两件事

运行监测采用独立的恢复候选，用来判断新的有效链路是否连续稳定。可在代理重启、PID/出口改变后确认“后台采样已恢复”，但 `launch_healthy` 不会因此变成 true，旧报告也不会更新成新的启动依据。只有新的完整检查才可重新准备启动入口；实际执行还必须有用户手动意图与提交前复检。

地区不符合保存偏好、监听身份不匹配等检查仍是异常，不因时间经过而恢复。代理预检模式中的 IPv6 覆盖 Warning 是明确的非阻断提醒；其他完整检查警告仍会阻断，不因后台恢复而放宽。IPv6 快照只在完整检查刷新，后台不承诺逐周期验证 IPv6 覆盖。

## 原生验收边界

本机实测保留真实本地采集和固定代理 Cloudflare；未切断代理、切换真实网络、强制休眠或启动真实客户端来制造异常。原生通知结果与用户实际看到的区别见 [通知诊断](NOTIFICATION_DIAGNOSTICS.md)。Windows原生支持仍未验收。
